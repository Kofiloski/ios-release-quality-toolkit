# Showcase scope and evidence

Date: 2026-11-07. Status: Accepted.

## Context and constraints

The owner asked for an independent assessment of whether the three popular-app
forks prove useful toolkit behavior and justify maintenance, then approved its
recommendations. Two independent Astra reviews found valid fixed native
baselines but no executed live release-generated UI flow. The forks require
different build/signing/project adaptations, and ordinary Actions artifacts
expire. Provider credentials remain unavailable.

## Decision

Keep DuckDuckGo as the active behavioral flagship. Preserve Firefox and Proton
Pass as public pinned integration references, with manual workflows and durable
native evidence; remove their recurring release triggers. Keep upstream
attribution and scope disclosures. Fix the two release-orchestration defects and
Firefox's unsupported-destination false-pass risk.

Strengthen the flagship with an explicitly labelled application fault using the
same unchanged native assertion before, during and after correction. Archive
successful native bundles, media, source identities and hashes on each fork's
engineering prereleases. Treat cold CI reproducibility, human onboarding, live
model planning and regression sensitivity as separate evidence.

## Alternatives

- Delete the extra forks: rejected because their existing integrations and
  independently verified baseline evidence remain useful public references.
- Keep all three tracking upstream equally: rejected because they do not yet
  add three distinct proofs of the central generated-release-testing behavior.
- Call fixed baselines or a seeded fault live AI regression discovery: rejected
  because neither executed an unattended planner or identified an upstream bug.
- Wait for model credentials before improving native evidence: rejected because
  controlled failure sensitivity and durable archiving can be verified now.

## Consequences

Recurring development is concentrated on one app while the other references can
age deliberately. New recurring apps should add a distinct demonstrated use
case. The controlled proof strengthens native assertion evidence but does not
complete unattended AI generation or an independent new-user adoption study.
