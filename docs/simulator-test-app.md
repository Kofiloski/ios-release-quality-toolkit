# Ice Cubes evaluation app

Use [Ice Cubes](https://github.com/Dimillian/IceCubesApp), a released SwiftUI Mastodon client, as the first evaluation app. The goal is a useful case study for iOS developers as well as a realistic diagnostic exercise. On November 3, 2026, GitHub reported 7,103 stars for Ice Cubes, 10,499 for NetNewsWire, and 13,071 for Firefox iOS. These are dated visibility signals, not audience or adoption forecasts. Ice Cubes is the first choice because its SwiftUI architecture directly exercises the toolkit's main UI-contract use case. NetNewsWire and Firefox are candidates for later UIKit coverage.

Pin the initial evaluation to [`98098b9c4b5928f89f338203193c2bf40ab7f38c`](https://github.com/Dimillian/IceCubesApp/tree/98098b9c4b5928f89f338203193c2bf40ab7f38c). The project is AGPL-3.0 licensed; retain its license and attribution, and review the license before distributing any modified app. Keep the app checkout, build products, and raw diagnostic data outside the distributable skill bundles. Do not imply endorsement by Ice Cubes or its maintainers.

## Source-backed starting flow

The pinned source exposes Settings while logged out: `IceCubesApp/App/Tabs/Tabs.swift` includes `.settings` in `loggedOutTab()` and `SidebarSections.loggedOutTabs`. The first flow therefore targets local display settings rather than authenticated posting, purchases, or live timeline content. Startup still initializes external services; this is not a claim that the entire app runs offline.

1. Launch an unmodified development build on a dedicated Simulator with no personal accounts. Record the source revision, configuration, bundle identifier, executable, UDID/runtime, locale, appearance, and reproduction times.
2. Reach Settings, then Display, using the actual exposed controls. Capture the screen and the failing automation client's UI tree if available. Discover current labels/types instead of inventing identifiers.
3. Record the initial system-color toggle value, change it once through the UI, and capture the resulting toggle and enabled/disabled color controls. `DisplaySettingsView.themeSection` binds that toggle to `Theme.followSystemColorScheme`.
4. Read the corresponding persisted preference through the resolved app store/domain, without modifying it. `Packages/DesignSystem/Sources/DesignSystem/Theme.swift` writes through `ThemeStorage` using the exact serialized key `followSystemColorSchme` (the spelling is intentional here because it matches upstream). Do not rename it or assume an app-group store merely because the app has an app-group entitlement.
5. Relaunch normally, return to Display, and check the same toggle value. Correlate a bounded app-log excerpt if the observed state is unexpected. Distinguish a missing plist value, a registered default, an in-memory update, and persisted state. Do not rely on a possibly stale live plist read; use the app's defaults domain through an available inspection helper, or a settled snapshot after termination.
6. If a real identifier/type/reachability failure occurs, apply the smallest app-side repair in the isolated checkout and replay the exact failing test. Do not manufacture an upstream defect to demonstrate the skill. A controlled fault, if later requested, must be isolated and explicitly labeled as injected.

The optional second flow toggles a haptic preference and verifies its saved flag and relaunch state. `HapticSettingsView.swift` binds the timeline toggle to `UserPreferences.hapticTimelineEnabled`, backed by `haptic_timeline`. Simulator success would establish preference behavior only, not physical haptic output.

These source references establish the candidate flow. At the pinned upstream revision the app scheme has no testables; package test schemes exist, but they do not establish coverage for this UI path. The local evaluation described below adds a separate test target and an app-owned focused test without changing production app source.

## Setup and execution

Read the checkout's `AGENTS.MD`, README, manifests, and relevant code before editing. Do not substitute a different app silently if setup fails.

For a fresh checkout, clone the public repository into an isolated development location, check out the exact revision above, and confirm `git rev-parse HEAD`. Follow the upstream setup instructions, use the intended installed Xcode through command-scoped `DEVELOPER_DIR`, and enumerate available Simulator destinations. Build the `IceCubesApp` scheme for the explicit Simulator destination with `CODE_SIGNING_ALLOWED=NO` and a separate DerivedData directory. Avoid creating an account or configuring production services merely to exercise the local settings flow. If a runtime prerequisite prevents that flow, report it and narrow the next step using the actual error.

Use the updated `ios-ai-ui-check` skill to collect the baseline and diagnostics. If repeatable coverage is requested, first inventory app-owned UI tests and launch hooks; use the existing scaffold dry-run before adding a test target. The public action remains provider-agnostic and the app retains its launch, interaction, and assertion logic.

## Evidence and publication

Keep the revision, environment, action record, before/after/relaunch screenshots, actual inspect/replay output, bounded redacted logs, and redacted preference result together. Store raw state separately from anything uploaded. Report which checks ran and which were unavailable. A view dump is not proof of an XCTest contract; a changed flag is not evidence of a remote service result.

A useful public case study shows a concrete symptom, the evidence used to distinguish its cause, the smallest justified change when one is needed, and replay evidence. If the flow passes, report the successful diagnostic exercise without implying a bug was found. Link the upstream app and exact revision. Publish only real captured results; do not invent screenshots, timings, failures, or claims of endorsement. Publishing a post or contacting maintainers is a separate user-authorized action.

## Verified local run: November 4, 2026

The initial sandbox preflight on November 3 could not reach GitHub or CoreSimulator. After the user enabled local access, both probes succeeded. The pinned source was cloned into an isolated `IceCubesApp-SkillsTest` checkout and built as app version 2.1.7 (3066), using Xcode 27.1 (27A9275), an iPhone 18 Pro Simulator running iOS 27.0, Debug configuration, a dedicated bundle prefix, and `CODE_SIGNING_ALLOWED=NO`. Commands selected Xcode through `DEVELOPER_DIR`; global `xcode-select` remained unchanged.

The native pass used Apple's `mcpbridge` and the actual exposed `DeviceInteractionSynthesize` tool after the user approved the signed Codex agent and test folder. It followed Xcode's bundled device-interaction skill, including that skill's required subagent delegation. No third-party inspector was needed. The native standalone session reported `NotRun` while its screenshot and hierarchy showed the activated app and PID; that field was recorded as a tooling inconsistency rather than used as an assertion. The interaction sessions were closed after use.

The exercise found two tooling issues before the final replay:

- **Generated runner compatibility:** the scaffold inherited Swift 6 from the app target, and its `XCUIApplication` properties were initialized in nonisolated helper types. The reusable template now isolates its UI helpers and test entry points to `@MainActor`, reads hierarchy state through a main-actor initializer, and captures failure PNG data on the main actor in asynchronous teardown. A real Simulator-SDK compiler regression test passes in Swift 6 with warnings treated as errors; the action repository's 86-test suite passed.
- **Scenario targeting:** the labeled `Match System` switch row contained an actual nested switch. Tapping the outer row's center left the value at 1. Native hierarchy hit points distinguished the outer row at `(201, 381)` from the inner control at `(340.5, 381)`. Tapping the inner control changed both reported values to 0 and enabled Tint Color. The focused XCTest now queries `app.switches["Match System"].switches.firstMatch`, after asserting exactly one nested switch. This corrected the test's target without modifying production app code.

The final `DisplaySettingsPersistenceUITests/testMatchSystemPersistsAfterRelaunch` replay passed: it reached Display Settings while logged out, established a known enabled state through the UI, toggled the actual switch off, asserted Tint Color became enabled, terminated and relaunched the app, and asserted the off state and enabled color control again. XCTest reported one passed test, zero failures, and zero skips. A fresh container lookup followed by stable reads after the app stopped confirmed the Boolean preference `followSystemColorSchme = false` on disk. Initial absence of the key was preserved as distinct from the app's enabled default.

The evidence is stored locally in the sibling `test-results/icecubes-2026-11-03/` directory: the directory date is the start date; completion was November 4 in Europe/Skopje. It includes the build log, failed-run evidence, native before/after screenshots and hierarchies, the final `.xcresult`, named relaunch screenshots/hierarchies, the focused test log and JSON summary, bounded app logs, and the selected preference result. Raw logs remain local; use only reviewed excerpts in a public case study.

This verifies one English, light-appearance Simulator settings flow. It does not establish full-app regression coverage, other locales or devices, haptic hardware behavior, production purchases, server-side behavior, or App Store readiness. XCTest also reported an AVAudioSession main-thread runtime warning; this run did not reproduce an audio hang or measure its performance impact. No app functional defect was established in the tested settings flow. The case study should focus on the diagnosed runner and targeting issues and the final evidence, without suggesting an upstream app bug or endorsement.

The scaffold was generated with `--skip-workflow`; the native pass and direct XCTest replay did not execute the GitHub composite Action, reusable workflow, or live model planner. They also did not compare published releases.

## Release comparison: November 4, 2026

The latest published GitHub release on this date was [2.1.6](https://github.com/Dimillian/IceCubesApp/releases/tag/2.1.6), at `c3a852fd9c3cf3fe1c01797f410ba9def098edd3`; its predecessor [2.1.5](https://github.com/Dimillian/IceCubesApp/releases/tag/2.1.5) resolves to `5782d683025265da7ba58f5463121c3be2bcdc02`. Both tests fail against the older revision and pass against the new one: the Polish duplicate-group warning and Catalan instance post-count string preserve their `%@` argument after the release fixes. These are resource checks, not on-screen rendering or full-release validation. Ten existing upstream tests were selected for pagination cursor, collection decoding, and posting-timer coverage; they were inspected, not rerun. The current Action does not automatically resolve release pairs or ingest changelogs. The planner also permits a launch-and-screenshot fallback, which cannot establish coverage of the release changes. Explicit release inputs and visible missing-context/coverage reporting are follow-up requirements, not implemented features. No live model request, exact-release build, release UI replay, or GitHub Actions run occurred during this comparison.

## Implemented release regression checks

The subsequent November 4 implementation in `ios-ai-ui-check` adds explicit `base-ref`, `head-ref`, and `release-notes-path` inputs, local ref resolution with checkout/head validation, saved complete diff/context, visible excerpt truncation, and failures for missing explicit/PR comparison history instead of an unrelated fallback. Explicit release scenarios must include a visibility/text assertion. Summaries limit their outcome to the executed scenario. The wrapper now supports an app-owned XCTest selector for stronger assertions; a separate fix prevents missing optional failure screenshots from interrupting final status reporting. These changes remain local and have not been published as a new Action release.

Two separate worktrees were built at the exact 2.1.5 and 2.1.6 commits with an identical app-owned Debug fixture and XCTest overlay. The fixture embeds the production account list and retains its pagination logic, injecting only a dedicated ephemeral URL session. It supplies A/B on the initial page, a numeric Link cursor unrelated to account IDs, and C/D on the second page. Tests assert unique rows, the requested cursor, and no extra page after the final response. Both blocked/muted UI tests fail on 2.1.5 with repeated initial-page requests and missing C/D; both pass on 2.1.6. This validates the app's already-released fix, without changing its production pagination implementation.

An app-owned shared Xcode scheme also ran ten existing tests successfully: four endpoint/cursor tests, four collection decoding tests, and two posting-timer cleanup tests. The Action maintenance suite passes 97 tests, including missing-context, malformed-event, smoke-only-release, truncation, and optional-attachment reporting cases. A first fixture attempt used a nonnumeric cursor unsupported by the existing parser; its failure is retained separately from the corrected runs.

Evidence is stored in the sibling `test-results/icecubes-release-rerun/` directory, including the human report, per-change coverage JSON, native XCTest results, real screenshots and hierarchies, videos, context/diff, test/build logs, fixture sources, and local replay scripts. New-release checks exercised the public planning/execution scripts and manifest writer locally; baseline reproduction used the same resolved scenarios on the separately built older source. Shared DerivedData requires rebuilding the selected checkout before replay; the helper does that instead of trusting a matching test-target name.

The model API planner, GitHub-hosted job, upload and PR-comment APIs remain unverified. Collection UI navigation/filtering, custom emoji headers, Mac Catalyst avatar behavior, production purchases and broader device/locale coverage remain outside the executed checks. The English-only collection strings remain an upstream translation-coverage question. No dependency on AXe or another external testing utility was introduced, and nothing was committed or published.
